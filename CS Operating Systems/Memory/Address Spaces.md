# Address Spaces

> **One-line summary**: An address space gives each process the illusion of exclusive, contiguous memory while the hardware maps virtual addresses to physical RAM.

## 🎯 Intuition
**The Core Idea:** Every process thinks it owns all of memory — the OS and MMU maintain this illusion by translating addresses behind the scenes.
**Analogy:** Imagine every tenant in an apartment building believes they live at "Apartment #1, Floor 1." The building manager (OS) + elevator system (MMU) secretly routes each tenant to their actual physical unit. Tenants never see each other's space, and they can't accidentally wander into the landlord's office (kernel).
**Why It Matters:** Address spaces are the foundation of memory protection, process isolation, and the ability to run programs compiled for address 0 at any physical location.

---

## ⚙️ Core Mechanics
### How It Works
An **address space** is the set of memory addresses that a process can legally reference. The OS gives each process the *illusion* of exclusive access to a contiguous block of memory, while the hardware translates these **logical (virtual) addresses** to **physical addresses** in RAM.

#### Why Address Spaces?
Without address space isolation, any process could overwrite any other process's data — or the kernel itself. Address spaces provide:

1. **Protection**: a process can only access memory the OS has granted to it.
2. **Relocation**: a program can be compiled to start at address 0 and loaded anywhere in physical RAM.
3. **Abstraction**: the programmer reasons about a simple flat address space; the OS handles the messy physical layout.

#### Base and Limit Registers
The simplest hardware implementation: each process has a **base** register (starting physical address) and a **limit** register (length of the region). Every memory access is checked: `base ≤ physical address < base + limit`. Violation triggers a hardware fault → OS terminates the offending process.

**Limitation:** cannot share code segments between processes; no support for non-contiguous allocation.

### Key Concepts

| Term | Meaning |
|------|---------|
| Logical (virtual) address | Address generated by the CPU; what the program sees |
| Physical address | Address on the memory bus; what DRAM actually receives |
| MMU | Memory Management Unit — hardware that translates logical → physical |

### Modern Address Space Layout (x86-64 Linux)

```
high  ┌────────────────────────┐
      │ Kernel (not accessible │ ← same kernel mapping in all processes
      │ from user space)       │
      ├────────────────────────┤ ~0xFFFF800000000000
      │ Stack (grows down)     │
      │ ...                    │
      │ Heap (grows up)        │
      │ BSS / Data             │
      │ Text (code, read-only) │
low   └────────────────────────┘ 0x000000000000
```

### Key Facts
- Every process has its own virtual address space — addresses in one process are independent of addresses in another.
- The MMU translates every memory access from virtual to physical — this happens in hardware, transparently.
- Base-and-limit is the simplest scheme; modern systems use paging for flexibility.
- The kernel is mapped into every process's address space (upper half on x86-64) but protected by permission bits.

## 🔬 Deep Dive
### Implementation Details
- **x86-64 virtual address space**: 48-bit virtual addresses (256 TiB) with canonical form — addresses must have bits 48–63 either all 0 (user space, lower half) or all 1 (kernel space, upper half). The "hole" in between is unmapped and causes a fault if accessed.
- **ASLR (Address Space Layout Randomisation)**: The kernel randomises the base addresses of the stack, heap, mmap region, and executable on each exec. This makes return-oriented programming (ROP) attacks harder because attackers cannot predict code/data locations.
- **`mmap()` and the address space**: Programs extend their address space dynamically via `mmap()` — mapping files, allocating anonymous memory, or creating shared regions. `malloc()` internally uses `mmap()` for large allocations and `brk()`/`sbrk()` for small ones.
- **Memory-mapped files**: `mmap(fd, ...)` maps a file's contents directly into the address space. Reads become memory loads; the page fault handler fetches pages from disk on demand. This is how shared libraries (.so/.dll) are loaded.

### Edge Cases and Pitfalls
- **Stack overflow**: If the stack grows past its limit (typically 8 MB on Linux), the process hits the guard page and receives SIGSEGV. In multithreaded programs, each thread has a separate, fixed-size stack — overflow is silent until it corrupts adjacent memory or hits a guard.
- **NULL pointer dereference**: Page 0 is intentionally left unmapped so that NULL dereferences cause an immediate fault rather than silently reading/writing address 0.
- **Kernel address leaks (Meltdown)**: Speculative execution on some CPUs could read kernel-mapped memory from user space. Mitigation: KPTI unmaps most kernel pages from user-space page tables, adding overhead to every syscall.
- **32-bit address exhaustion**: A 32-bit process has only 4 GiB of virtual address space (3 GiB user / 1 GiB kernel on Linux). Large applications (databases, browsers) can exhaust this even with abundant physical RAM.

### Real-World Systems
- **Linux**: Each process has an `mm_struct` describing its address space; VMAs (Virtual Memory Areas) define each mapped region (code, data, stack, mmap'd files). `/proc/[pid]/maps` shows the address space layout.
- **Windows**: The Virtual Address Descriptor (VAD) tree tracks reserved/committed regions. User space is 0–0x7FFFFFFFFFFF (128 TiB); kernel space above. `VirtualAlloc()` / `VirtualFree()` manage regions.
- **macOS**: Mach VM subsystem manages address spaces via "VM maps" containing "VM entries." `mach_vm_allocate()` is the low-level allocation; `mmap()` is available via BSD compatibility.

## 🏋️ Practice
### Warm-Up (5 min)
1. What three properties do address spaces provide, and why does each matter?
2. What is the difference between a logical address and a physical address? Which does the programmer see?
3. Why is page 0 left unmapped in most operating systems?

### Core Problems
1. **Address translation**: A system uses base-and-limit registers. Process A has base=0x4000, limit=0x3000. Process B has base=0x8000, limit=0x2000. (a) Translate logical address 0x1500 for Process A. (b) What happens if Process A accesses logical address 0x3500? (c) Can Process A access Process B's memory? Why not?
2. **Address space layout analysis**: Run `cat /proc/self/maps` on a Linux system (or describe the expected output). Identify the text, data, heap, stack, and shared library regions. Explain why the stack and heap grow in opposite directions. What is the purpose of the `[vdso]` and `[vsyscall]` entries?

### Challenge
ASLR randomises the positions of stack, heap, and libraries on each exec. An attacker wants to exploit a buffer overflow in a server that calls `fork()` (not `exec()`) to handle connections — meaning the address space layout is the same in every child. Design an attack strategy that defeats ASLR under this model. Then propose a mitigation: should the server re-exec instead of fork? What are the performance trade-offs?
