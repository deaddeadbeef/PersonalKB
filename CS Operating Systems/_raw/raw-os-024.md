# Boot Process

## Summary

The boot process is the sequence of steps a computer executes from power-on to a running operating system. On x86 systems, this begins with firmware initialization. Legacy BIOS systems execute POST (Power-On Self-Test), which checks essential hardware (RAM, CPU, video), then loads the first 512-byte sector (Master Boot Record) from the boot device into memory at address 0x7C00 and transfers control to it. Modern UEFI (Unified Extensible Firmware Interface) replaces BIOS with a richer firmware environment that can read FAT32 partitions, supports GPT partition tables (enabling disks larger than 2 TB), and loads EFI boot applications directly. UEFI also supports Secure Boot, which verifies cryptographic signatures on the bootloader and kernel to prevent rootkits from hijacking the boot chain.

The bootloader is the next stage. GRUB (GRand Unified Bootloader) is the standard Linux bootloader. GRUB operates in two stages: a small first stage in the MBR or EFI partition loads the larger second stage from the filesystem, which presents a menu, parses its configuration (`grub.cfg`), and loads the kernel image and initial ramdisk into memory. The bootloader passes a kernel command line containing parameters such as the root filesystem device, console settings, and boot options.

Once loaded, the Linux kernel decompresses itself, initializes the CPU, sets up memory management, and mounts the initial RAM filesystem (initramfs). The initramfs is a temporary root filesystem containing essential drivers and tools needed to locate and mount the real root filesystem—critical when the root device requires drivers not compiled into the kernel (e.g., RAID, LVM, encrypted disks). After mounting the real root, the kernel executes the init process (PID 1). Traditionally this was SysVinit with sequential runlevels (0–6). Modern Linux distributions use systemd, which parallelizes service startup using dependency graphs and targets (analogous to runlevels: `multi-user.target` ≈ runlevel 3, `graphical.target` ≈ runlevel 5). systemd tracks services via cgroups, supports socket activation for on-demand service launch, and provides the `journald` logging framework.

## Key Claims

- UEFI replaces BIOS with a firmware environment capable of reading filesystems, using GPT partition tables, and enforcing Secure Boot cryptographic verification of the boot chain
- The bootloader (GRUB) bridges firmware and kernel by loading the kernel image and initramfs into memory and passing boot parameters via the kernel command line
- initramfs provides a temporary root filesystem with drivers necessary to access the real root device, enabling boot from complex storage configurations like RAID, LVM, or LUKS encryption
- systemd replaced SysVinit to enable parallel service startup, dependency-based ordering, and cgroup-based service tracking, significantly reducing boot times
- Secure Boot creates a chain of trust from firmware through bootloader to kernel, preventing unsigned or tampered code from executing during the boot process

## Atomic Facts

1. The legacy BIOS MBR is exactly 512 bytes, with the boot code in the first 446 bytes, the partition table in the next 64 bytes, and a 2-byte magic number (0x55AA) at the end
2. GRUB2's configuration file is typically located at `/boot/grub/grub.cfg` and is generated by `grub-mkconfig` from scripts in `/etc/grub.d/`
3. The initramfs is a cpio archive compressed with gzip, xz, or zstd, unpacked by the kernel into a tmpfs at boot
4. systemd targets replace SysVinit runlevels: `rescue.target` (single-user), `multi-user.target` (multi-user CLI), `graphical.target` (GUI desktop)
5. The kernel command line parameter `root=/dev/sda2` tells the kernel which block device contains the root filesystem to mount
6. UEFI Secure Boot uses X.509 certificates stored in firmware NVRAM; Microsoft's certificate is pre-enrolled on most hardware, which Linux distributions address via signed shim bootloaders

## Significance

The boot process is the foundation of system integrity—every security guarantee of a running OS depends on a trustworthy boot chain. Understanding boot sequence details is essential for system administration, troubleshooting startup failures, and comprehending how security mechanisms like Secure Boot establish trust. The evolution from BIOS to UEFI and SysVinit to systemd reflects broader OS trends toward parallelism, security, and capability.
